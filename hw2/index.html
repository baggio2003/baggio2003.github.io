Homework 2: Wallet Seed → Ethereum Address Pipeline

Deep dive into Ethereum's layered cryptographic standards: BIP-39, BIP-32, BIP-44, secp256k1, Keccak-256, and EIP-55, with empirical evaluation of the Strict Avalanche Criterion (SAC) and bit uniformity.

1. Conceptual Classification of Cryptographic Primitives

Building a modern non-custodial cryptocurrency wallet relies on distinct primitive categories, each engineered to meet orthogonal mathematical constraints:

Category Primary Purpose Core Mathematical Properties Pipeline Component
Key Generation Pure source entropy sampling Non-deterministic, uncorrelated, maximum Shannon entropy ($H \ge 128 \text{ bits}$) via CSPRNG CSPRNG Entropy (128–256 bits)
Key Derivation (KDF) One-way deterministic expansion Computationally hard / memory-hard stretching to resist dictionary attacks; pseudo-randomness BIP-39 (PBKDF2), BIP-32 (HMAC-SHA512)
Public-Key Cryptography Asymmetric identity & signatures Algebraic group homomorphism; intractability of the reverse trapdoor (ECDLP) secp256k1 ($Q = k \cdot G$)
Cryptographic Hashing Fixed-size digest & compression Pre-image resistance, collision resistance, algebraic structure destruction, Strict Avalanche Criterion Keccak-256
Checksum Accidental typo detection High Hamming distance sensitivity to character swaps and typos; zero secrecy required EIP-55 (Capitalization mask)
Encoding Bijective textual representation Reversible, 1-to-1 mapping for machine/human transportability; preserves underlying entropy Hexadecimal (`0x...`)

2. Step-by-Step Architecture: From Seed to Checksummed Address

Ethereum decouples wallet generation into a deterministic sequence of modular standards. Each phase transforms raw entropy into usable cryptographic identifiers through precise mathematical mappings:

Phase 1: BIP-39 — Mnemonic Words & Binary Seed

Key Management
Input: 128 bits of CSPRNG Entropy
Output: 12 Mnemonic Words & 512-bit Binary Seed

Raw binary entropy is prone to transcription errors. BIP-39 encodes this entropy into human-readable words and stretches it into a cryptographic seed:

  • Checksum append: A 4-bit checksum ($\text{SHA-256}(\text{entropy})[:4]$) is appended to the 128-bit entropy, producing 132 bits.
  • Word mapping: The 132 bits are split into 12 chunks of 11 bits ($2^{11} = 2048$). Each chunk indexes an exact word from the BIP-39 dictionary.
  • Key stretching (PBKDF2): The words are hashed over 2048 rounds of HMAC-SHA512 to produce a 512-bit master seed, drastically increasing brute-force cost:
$$\begin{aligned} \text{Seed} = \text{PBKDF2}\big( & \text{PRF} = \text{HMAC-SHA512}, \\ & \text{Password} = \text{mnemonic}, \\ & \text{Salt} = \text{"mnemonic"} + \text{passphrase}, \\ & c = 2048, \quad \text{dkLen} = 64 \text{ bytes} \big) \end{aligned}$$

Phase 2: BIP-32 & BIP-44 — Hierarchical Deterministic (HD) Derivation

Key Derivation
Input: 512-bit Seed & Derivation Path
Output: 256-bit Private Key ($k$) & Chain Code

To avoid backing up multiple independent keys, BIP-32 and BIP-44 organize an infinite tree of deterministic key pairs under a single root seed:

  • Master Key generation: $\text{HMAC-SHA512}(\text{Key} = \text{"Bitcoin seed"}, \text{Data} = \text{Seed})$ produces the 256-bit Master Private Key (left half) and 256-bit Master Chain Code (right half).
  • Standardized derivation path: BIP-44 enforces a structured five-level derivation hierarchy: $$\text{Path} = m \,/\, \text{purpose}' \,/\, \text{coin\_type}' \,/\, \text{account}' \,/\, \text{change} \,/\, \text{address\_index}$$
  • Ethereum path: m/44'/60'/0'/0/0 targets coin type $60'$ (Ethereum). Hardened derivation ($'$) isolates branches so a leaked child key cannot compromise parent or sibling keys.

Phase 3: secp256k1 — Asymmetric Public Key Generation

Asymmetric Crypto
Input: 256-bit Private Key ($k$)
Output: 64-byte Uncompressed Public Key ($Q$)

The private key scalar $k \in [1, n-1]$ is mapped to an elliptic curve point $Q$ via scalar multiplication with the standardized base generator $G$:

$$Q = k \cdot G = (x_Q, y_Q) \quad \text{on } y^2 \equiv x^3 + 7 \pmod p$$

In Ethereum, the uncompressed public key is the direct 64-byte concatenation $(x_Q \parallel y_Q)$ without the legacy 0x04 prefix. The ECDLP guarantee ensures that recovering $k$ from $Q$ is computationally impossible, allowing $Q$ to authenticate signatures safely.

Phase 4: Keccak-256 Hashing & 20-Byte Address Truncation

Hashing & Compression
Input: 64-byte Public Key $(x_Q \parallel y_Q)$
Output: 20-byte (160-bit) Raw Address

The 64-byte public key is hashed using the original Keccak-256 sponge function:

$$H = \text{Keccak-256}(x_Q \parallel y_Q) \quad (32 \text{ bytes})$$
$$\text{RawAddress} = H[12 \dots 31] \quad (\text{last } 20 \text{ bytes / } 160 \text{ bits})$$

Discarding the first 12 bytes reduces state trie storage overhead across nodes. The remaining 160 bits provide an address space of $2^{160} \approx 1.46 \times 10^{48}$ unique accounts, well beyond any realistic accidental collision threshold ($2^{80}$ via birthday bound).

Phase 5: EIP-55 — Mixed-Case Checksum Encoding

Error Detection
Input: 40-character Lowercase Hex Address
Output: Mixed-Case Checksummed Address

To avoid changing the 20-byte address length while preventing catastrophic typographical errors, EIP-55 embeds integrity information into the capitalization of letters ($a\text{--}f$):

  1. Compute the Keccak-256 hash of the 40-character lowercase address string: $H_{\text{addr}} = \text{Keccak-256}(\text{lowercase}(\text{Address}))$.
  2. For each character at index $i$ in the address, inspect the $i$-th nibble (4 bits) of $H_{\text{addr}}$:
$$\text{Char}_i = \begin{cases} \text{UPPERCASE}(\text{Char}_i) & \text{if } H_{\text{addr}}[i] \ge 8 \quad (\text{MSB} = 1) \\ \text{lowercase}(\text{Char}_i) & \text{if } H_{\text{addr}}[i] < 8 \quad (\text{MSB} = 0) \end{cases}$$

Digits ($0\text{--}9$) remain unaffected. A single altered character scrambles the entire hash, producing mismatched capitalization that causes wallet clients (like MetaMask) to reject invalid destination addresses.

5. Historical Timeline & Design Rationale

Chronological Evolution of Wallet Primitives

  • 1977 — RSA: First practical public-key cryptosystem based on integer factorization, establishing the concept of one-way trapdoors.
  • 2001 — SHA-2 / SHA-512: Standardized by NIST using the Merkle-Damgård construction. Adopted in BIP-39 for PBKDF2 stretching.
  • 2012 — BIP-32: Pieter Wuille introduces hierarchical deterministic wallets to replace dangerous manual backups of random key pools.
  • 2013 — BIP-39: Standardizes human-readable mnemonics, replacing fragile hex strings with phonetic, typo-resistant wordlists.
  • 2014 — BIP-44: Establishes multi-account, multi-coin deterministic derivation tree paths.
  • 2015 — SHA-3 / FIPS 202: NIST standardizes Keccak with a domain separation padding shift from 0x01 to 0x06. Because Ethereum was already live on testnet/mainnet in 2014–2015, it preserved the original Keccak-256 algorithm.
  • 2016 — EIP-55: Vitalik Buterin introduces mixed-case capitalization checksums to prevent typo-driven fund losses without breaking address length.

Why Not a Single Unified Algorithm?

A secure wallet cannot be built from a single primitive because their core mathematical requirements are contradictory:

  • Digital Signatures require Group Homomorphism: secp256k1 preserves $(k_1 + k_2)G = k_1 G + k_2 G$, allowing ECDSA signature verification. If a hash function were homomorphic, it would be catastrophically broken.
  • Hashing requires Total Structure Annihilation: Keccak-256 destroys all algebraic relations to guarantee collision resistance and SAC. It has no trapdoor and cannot sign transactions.
  • Key Derivation requires Adjustable Slowness: PBKDF2 runs 2048 iterations to foil hardware brute-forcers. Using PBKDF2 inside consensus for transaction hashing would paralyze the blockchain.

6. Practical Wallet Software Context (MetaMask, Rabby, Rainbow)

When you import a 12-word recovery phrase into modern Web3 wallets like MetaMask, Rabby, Rainbow, or hardware wallets like Ledger:

  • The wallet performs BIP-39 PBKDF2 stretching in an isolated cryptographic vault.
  • It derives account 0 via BIP-44 path m/44'/60'/0'/0/0, generating private key $k$ and public key $Q$.
  • It computes Keccak-256 over $Q$ and displays the address formatted with EIP-55 checksum capitalization.
  • When adding "Account 2", the software does not ask for new words; it simply increments the index to m/44'/60'/0'/0/1 deterministically.
