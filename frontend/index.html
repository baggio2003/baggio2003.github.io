Statistical Analysis and Interpretation

Methodology, transformation algorithms, hypothesis tests, results and conclusions of the file-transfer analysis.

A. Introduction B. Algorithms C. Metrics D. Hypothesis testing E. Tests F. Multi-file G. Conclusions

A. Introduction and Research Objective

Research question Can entropy alone reliably distinguish compressed data from encrypted data?

Objective. We study the statistical properties of three representations of the same file, and ask whether compression and encryption produce different distributions and whether the metrics below can detect the difference.

Plaintext

The original file. Usually shows redundancy: some byte values are far more frequent than others.

Compressed (GZIP)

DEFLATE removes much redundancy, but the output is a deterministic transformation of a structured source and keeps a recognisable format (header, blocks).

Encrypted (AES-256-CTR)

The plaintext is XORed with a pseudorandom keystream, so the output is expected to be statistically close to uniform bytes.

Analysis approach.

  • Descriptive analysis: observe entropy, byte frequencies and bit distribution, chunk by chunk.
  • Inferential analysis: apply hypothesis tests (chi-square, bit monobit) to check specific properties of the observed distributions.

B. Transformation Algorithms (Compression and Encryption)

Before slicing the file into 1 MB chunks, the browser generates three distinct binary streams in memory (transform.js) using native Web APIs. Understanding how each algorithm transforms the input bytes explains why their statistical distributions differ.

1. Lossless Compression: GZIP (DEFLATE)

Implementation: Browser native CompressionStream('gzip') API (RFC 1952 / RFC 1951).

How it works: GZIP is based on the DEFLATE algorithm, which removes statistical redundancy in two sequential stages:

  • LZ77 (Sliding-Window Dictionary): scans the input stream for repeated byte sequences (up to 32 KB back) and replaces duplicates with compact pointer tuples \(\langle \text{distance}, \text{length} \rangle\).
  • Huffman Coding (Entropy Coding): replaces frequent symbols with shorter prefix-free bitstrings and rare symbols with longer ones, approaching the theoretical Shannon limit:
    \[ L_{\text{avg}} = \sum_{i} p_i \, l_i \approx H(X) \]

Why it is not truly uniform: Although Huffman coding packs bits tightly (pushing Shannon entropy close to \(8\text{ bits/byte}\)), a GZIP stream still contains deterministic structural elements: a 10-byte header (1f 8b 08...), dynamic Huffman tree descriptions at the beginning of each block, and an 8-byte trailer (CRC-32 checksum and original file size). Because it optimizes for compactness rather than cryptographic indistinguishability, slight byte-level biases remain detectable by the \(\chi^2\) test.

2. Symmetric Encryption: AES-256-CTR

Implementation: Browser native Web Crypto API (crypto.subtle.encrypt, NIST SP 800-38A).

How it works: The Advanced Encryption Standard with a 256-bit key (14 transformation rounds of SubBytes, ShiftRows, MixColumns, and AddRoundKey) is operated in Counter (CTR) mode, turning the block cipher into a synchronous stream cipher:

  • A random 128-bit initial counter block \(T_1 = \text{Nonce} \parallel \text{Counter}\) is generated via CSPRNG (crypto.getRandomValues).
  • For each 16-byte block \(k\), the cipher encrypts the incremented counter to produce a pseudorandom keystream block \(S_k = \operatorname{AES}_{K}(T_k)\).
  • The ciphertext is obtained by bitwise XORing the plaintext \(P\) with the keystream \(S\):
    \[ C_i = P_i \oplus S_i \]

Why it behaves like a uniform random source: Under the standard assumption that AES acts as a Pseudorandom Permutation (PRP), the keystream \(S_i\) is computationally indistinguishable from independent uniform bytes in \(\{0,\dots,255\}\). XORing any plaintext distribution with an independent uniform distribution yields a strictly uniform output, with no padding overhead and no container headers.

C. Statistical Metrics

Each chunk of N bytes is summarised by the metrics below. These are descriptive statistics: they describe the data, they do not test anything by themselves.

1. Shannon Entropy ↑ Entropy Chart

\[ H(X)=-\sum_{i=0}^{255}p_i\log_2(p_i) \]

\(p_i\) is the observed probability (relative frequency) of byte value \(i\). Entropy measures the uncertainty of the byte distribution, in bits per byte, between 0 and 8.

Interpretation: the maximum, 8, is reached when all 256 values are equally likely. High entropy does not prove encryption: compressed data can also have values close to 8. Entropy depends only on the histogram, so it ignores byte order.

2. Byte Frequency Distribution ↑ Byte Chart

\[ O_i=\#\{k : X_k=i\},\quad i=0,\dots,255 \]

A byte takes one of 256 values (0–255). The distribution counts how many times each value appears.

Interpretation: a uniform distribution has similar counts for all values; a non-uniform one has some values much more frequent than others (typical of text).

3. Bit Distribution ↑ Bit Chart

\[ P(1)=\frac{N_1}{N_{\text{bits}}},\qquad P(0)=\frac{N_0}{N_{\text{bits}}} \]

Each byte has 8 bits; the program counts bits equal to 0 and to 1 (\(N_{\text{bits}}=8N\)).

Interpretation: a balanced distribution has both proportions close to 50%. Balance is necessary for random-looking data but not sufficient.

4. Byte Mean and Standard Deviation ↑ Summary Card

Bytes are treated as numbers in [0, 255]. The mean is their average value; the standard deviation measures dispersion around it. For a discrete uniform distribution on {0,…,255}:

\[ \mu=127.5,\qquad \sigma=\sqrt{\tfrac{256^2-1}{12}}\approx 73.90 \]

Interpretation: these are reference values under uniformity, not values every file must reach. They are not a normality test.

D. Statistical Hypothesis Testing

The reasoning needed to read the statistical tests in section E and the results tables above.

1. Null and Alternative Hypotheses

H₀ (null): the reference condition of the test.
H₁ (alternative): the opposite condition.
Test H₀ H₁
Chi-square Byte distribution is uniform Byte distribution is not uniform
Bit monobit P(1) = 0.5 P(1) ≠ 0.5

The hypotheses concern specific properties. They do not classify a file as compressed or encrypted.

2. Significance Level

\(\alpha\) is the probability of rejecting H₀ when H₀ is true (false positive rate). The code currently uses:

\[ \alpha=0.01 \]

so the decision threshold is 1%. Even on perfectly uniform data, about 1% of tests will reject H₀ by chance.

3. p-value

\[ p=P(\text{result at least as extreme as observed}\mid H_0) \]
  • If \(p < \alpha\): reject H₀.
  • If \(p \ge \alpha\): do not reject H₀.
  • Not rejecting H₀ does not prove it true.
Illustrative examples (not project results)
p-value Decision at α = 0.01
0.300 Do not reject H₀
0.020 Do not reject H₀
0.0004 Reject H₀

4. Z-score

\[ Z=\frac{\text{observed}-\text{expected}}{\text{standard deviation}} \]

The Z-score is the distance between an observed result and its expected value, in standard deviations. Under H₀ it is approximately N(0,1); the shaded tails are the rejection region for a two-sided test at α = 0.01 (|Z| > 2.576).

E. Statistical Tests

1. Chi-Square Goodness-of-Fit Test ↑ Chi-Square Chart

Purpose: check whether the byte distribution is compatible with a uniform distribution over 256 values.

H₀: byte distribution is uniform.
H₁: byte distribution is not uniform.
\[ E_i=\frac{N}{256},\qquad \chi^2=\sum_{i=0}^{255}\frac{(O_i-E_i)^2}{E_i} \]

\(O_i\) is the observed count and \(E_i\) the expected count. There are \(\nu=256-1=255\) degrees of freedom. Under H₀, \(\chi^2\sim\chi^2_{255}\) approximately, and the p-value is the upper tail:

\[ p=P\left(\chi^2_{255}\ge\chi^2_{\text{obs}}\right) \]

Conceptual example: for a chunk of N = 1,048,576 bytes, each value is expected \(E_i=4096\) times. Counts close to 4096 for every value give a small \(\chi^2\); strong departures (e.g. many bytes concentrated on few values) give a large \(\chi^2\) and a small p-value.

Interpretation: the result indicates compatibility or incompatibility with uniformity. It does not identify encryption.

Limits: the approximation needs adequate expected counts (rule of thumb \(E_i\ge5\)); with large N tiny deviations become significant; the test ignores byte order.

2. Bit Monobit Test ↑ Bit Balance Chart

Purpose: check the balance between 0 and 1 bits.

H₀: P(1) = 0.5.
H₁: P(1) ≠ 0.5.
\[ Z=\frac{|N_1-N_0|}{\sqrt{n}}=\frac{|2N_1-n|}{\sqrt{n}},\qquad n=8N \]
\[ p=2\,[1-\Phi(Z)]=\operatorname{erfc}\!\left(\tfrac{Z}{\sqrt2}\right) \]

Under H₀, \(N_1\sim\text{Binomial}(n,0.5)\), approximated by a normal distribution for large n (central limit theorem). If \(p<\alpha=0.01\), H₀ is rejected: the bits are not balanced.

Limits: balance is not randomness. A sequence like 0101… is perfectly balanced yet clearly not random; the test detects neither patterns nor dependence between bits.

4. Key Findings

  • Compression substantially increases entropy. The average entropy rises from 4.303 bits/byte in plaintext to 7.914 bits/byte after GZIP compression, approaching the theoretical maximum of 8 bits/byte.
  • High entropy does not imply a uniform byte distribution. Despite its high entropy, GZIP is rejected by the Chi-square test in all six files. This shows that entropy alone cannot capture all statistical properties of the data.
  • The Monobit test provides a different perspective. It rejects H₀ for five out of six GZIP files, while the remaining file has a median p-value above the significance threshold. Therefore, bit balance alone does not consistently distinguish compressed from encrypted data.
  • AES results are consistent across the analysed files. None of the six files leads to rejecting H₀ in either test. This is consistent with the expected pseudorandom appearance of encrypted output, but does not establish cryptographic security.

5. Limitations

  • The dataset contains only six heterogeneous files and is not necessarily representative of all file types.
  • Files have different sizes and numbers of chunks. Chunks belonging to the same file are not independent file-level observations.
  • The median p-value is used as a descriptive summary. Multiple statistical tests increase the overall false-positive probability.
  • Entropy and the selected statistical tests examine only specific statistical properties of the data. They cannot establish cryptographic security or prove randomness.

G. Discussion and Conclusions

1. Entropy Limitations ↑ Entropy Chart

Shannon entropy measures the distribution of byte values and is bounded by 8 bits per byte. Both compressed and encrypted data can approach this maximum, making them difficult to distinguish using entropy alone. Furthermore, entropy ignores byte order and other structural properties. A file that is already compressed, such as a JPEG image or a video, may also exhibit high entropy before any additional transformation.

2. Contribution of Additional Statistical Metrics ↑ Chi-Square Chart ↑ Bit Chart

Additional metrics provide complementary information about the data. The Chi-square test examines the uniformity of the byte distribution, while the Monobit test evaluates the balance between zeros and ones. Our results show that these tests can reveal differences that entropy alone does not capture. However, they assess only specific statistical properties and cannot identify the transformation applied to a file with certainty.

3. Interpretation of the Multi-file Results ↑ Multi-file Chart

The comparison across six file types confirms that compression substantially increases entropy, with GZIP reaching an average of 7.914 bits per byte, compared with 4.303 bits per byte for plaintext. AES-256-CTR reaches 8 bits per byte across all analysed files.

Despite the small entropy difference between GZIP and AES, the Chi-square test rejects the uniformity hypothesis for all six GZIP files and for none of the AES files. The Monobit test rejects the bit-balance hypothesis for five GZIP files and none of the AES files. This demonstrates why combining different statistical indicators provides a more informative comparison.

These findings are consistent with the expected statistical behaviour of compressed and encrypted data in our experiment. Nevertheless, they should be interpreted as observations about the analysed files, rather than universal properties of every compression or encryption algorithm.

4. Experimental Limitations

  • The experiment includes six files, which represent a limited and heterogeneous sample.
  • File sizes and chunk counts differ, and chunks from the same file cannot be treated as independent file-level observations.
  • Statistical tests have a false-positive probability determined by α. Running multiple tests requires considering the overall false-positive rate.
  • Large sample sizes can make tests detect very small deviations, while small samples may reduce their statistical power.
  • Not rejecting H₀ means there is insufficient evidence against the tested hypothesis; it does not prove randomness or encryption.

5. Final Answer

Can entropy alone reliably distinguish compressed data from encrypted data?

No. Our experiment shows that both compressed and encrypted data can exhibit entropy values very close to the theoretical maximum of 8 bits per byte. Across the six analysed files, GZIP reaches an average entropy of 7.914 bits per byte, while AES-256-CTR reaches 8 bits per byte. Furthermore, some original files, such as the JPEG and video, already have high entropy in their plaintext representation.

Additional statistical metrics provide useful complementary information. In our dataset, the Chi-square test consistently detects deviations from a uniform byte distribution in GZIP data, whereas none of the AES files leads to rejecting this hypothesis. The Monobit test also identifies differences in most GZIP files, although it does not distinguish every case.

Therefore, combining entropy with other statistical features provides a more informative way to compare compressed and encrypted data. However, these tests cannot prove that a file is encrypted, establish its security, or identify the transformation that produced it. They only assess specific properties of the observed data.

Finally, the conclusions are limited to the six files included in our experiment. A broader dataset, with more file types and independent samples, would be necessary to assess whether these observations generalize to other data.
